### 1. 人做什么，agent 做什么

**Agentic Engineering**（智能体工程）是在 coding agent 协助下交付软件。这里的 agent 在循环里调用工具、看结果、再调整，直到目标达成或触发停止条件。Cursor、Claude Code、Codex 这一类 coding agent 的交付应结合代码执行、测试或 CI 的反馈；仅生成代码不足以确认软件能运行。

**Vibe Coding**（氛围编程）来自 Karpathy：用自然语言要结果，几乎不看代码。它适合低风险原型和个人小工具。日常让模型写代码，就是普通开发，不必都叫做 vibe coding。

分界看两件事：人是否理解并承担交付，以及有没有可执行的验证。可以少看逐行实现，责任仍在人。先看过往表现，出了问题要能往下查。

高质量产出来自：清楚的目标和验收、仓库里找得到的上下文、稳定的工具、可执行的验证，以及人对关键路径负责。

| | Vibe Coding | Agentic Engineering |
| --- | --- | --- |
| 做法 | 改提示，直到看起来对 | 目标 → 按需计划 → 实现 → 验证 → 记下来 |
| 人 | 临时指挥 | 定取舍、约束和验收，并担责 |
| 上下文 | 聊天记录 | 仓库里的短规则、文档、计划和测试 |
| 质量从哪来 | 模型当次发挥 | 约束、测试、审查和自动化门禁 |
| 常见翻车 | 需求漂移、隐性债 | 上下文过载、权限过大、验证不够 |

人的时间放在产品判断、架构约束和验证上，同时仍要能读代码、会调试。先定必要边界，随实现再收紧设计。核心业务、权限、安全、数据迁移、计费、并发和异常恢复要人看。复杂任务先看计划，再看 diff 和测试结果。

动手前把需求说清楚：一句明确指令，或几轮把边界问清。学新技术时，优先掌握架构、生态约定、数据设计、调试和部署；样板实现可以交给 AI。不要假设模型会永久记住纠正。教训写回规则、测试、检查脚本或明确的记忆机制，下次 agent 才有机会用上。

#### 原则

1. **验收先于实现**。小改动写清目标、约束和怎样算做完。复杂需求再补用户路径、数据契约、边界和非目标。Spec 是约定，小任务不必单独成文。
2. **只写代码里看不出来的上下文**。命令、和语言默认不同的约定、危险边界，放在仓库里。目录结构让 agent 自己看。
3. **一次一个可验证切片**。做完系统仍能跑。相关测试和文档可以一起改。夹带的重构另开任务。
4. **用确定性工具验收**。类型、lint、测试、浏览器里走一遍。测试对的是断言，验收对的是需求，两套都要有。
5. **关键决策人看**。AI 可以先审。安全、资金、权限、迁移必须人看。
6. **按代价选模型和工具**。样板可先试更快的模型；跨模块、疑难和高风险可用更强的，但最终看真实任务的成功率、延迟和总成本，包含重试与人工返工。格式化、计算、lint、测试交给确定性工具。已有可靠的 CLI 时，用 CLI。
7. **模型升级后重查脚手架**。Harness 里很多步骤是在补「当前模型还做不到的事」。[OpenAI 谈 GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)：文档按任务读，不必每次改动前通读整库；Skill 描述写短，并写清何时该用，过宽会把不相关的 Skill 拉进上下文；过细的步骤，以及为旧模型写的「先问再做」，会让更强的模型停在你其实允许继续的地方。已知无生产副作用的检查，可以写明自动跑、自动修。是否删减，用自己的任务验证。验收标准仍然写清。

精通一个主力工具，弄清它的上下文、权限和验证。用真实项目走通：澄清 → 计划 → 实现 → 测试 → 审查 → 部署。模型越强，产品判断、架构、安全和验证越值钱。

### 2. 从需求到交付

#### 工作建议

全栈和一人公司做新功能，默认三步。聊天记录不算规格。人改完需求文档，放进仓库，再写代码。

1. **纯沟通：ChatGPT 聊天。** 问清用户、场景、怎样算做完、不做的事。留下已确认和待确认。
2. **产出需求文档：ChatGPT 工作。** 写成目标、范围、验收、非目标、字段名。要对齐现有接口时，在 Cursor 里对着代码写，仍是这一步。
3. **实现这一条切片：Codex、Cursor。** 已有仓库里的页面用二者之一，浏览器走主路径和一条失败路径。一次交一条纵向切片：输入、接口、数据、权限、页面、验收命令；字段与契约用后文同一套名字。独立小站，ChatGPT 工作也能做。

材料已经在腾讯会议、企业微信、微盘、腾讯文档里时，**WorkBuddy** 做沟通和需求文档。它也能做代码、网站、小程序和设计稿；已有仓库里的实现，默认仍交给 Codex 或 Cursor。

1. **沟通**：读群聊、邮件、会议转写和智能纪要。会前查忙闲并安排会议。会后写结论和待办。
2. **需求文档**：按讨论写成智能文档或 Word，链接发回群，发出前本人确认。只写明确说过的内容，其余标待确认。

验收一句话说清的小任务不必单独成文，小改和修 bug 直接用 Cursor。一人公司的提案、报价、对外说明仍用 ChatGPT 工作。

**Harness** 是包在模型外面的运行环境：工具、上下文、权限、状态、反馈和停止条件。默认路径是探索 → 计划 → 实现 → 验证 → 记下来。先用现有工具跑通交付，再补实际缺少的能力。

- **小**：直接实现并验证。
- **中**：先看相关代码，动手前看过计划。
- **大或跨会话**：按需要加进度记录、检查点、独立 worktree，以及一个没参与实现的审查。子任务能独立拆开时才并行。

#### 2.1 仓库里放什么

| 放什么 | 做什么 | 注意 |
| --- | --- | --- |
| `AGENTS.md` | 每次都用得上的短入口 | 当目录页。命令、非默认约定、不许做的事、哪类任务再读哪篇 |
| `docs/` | 架构、契约、计划 | 有内容再写。入口负责指路，正文不要塞进默认上下文 |
| Skills | 重复流程 | 名称和描述用于发现，正文和资源按需加载。规范见 [Agent Skills](https://agentskills.io/specification) |
| 测试、lint、hook | 真正挡住错误 | 自然语言规则只是提示。会出事的约束要能在提交前失败 |

[Gloaguen 等人 2026 年的评测（v3）](https://arxiv.org/abs/2602.11988v3)在所测仓库任务中，未发现上下文文件普遍提高任务成功率，推理成本平均增加超过两成。这是特定评测下的结果；规则应写代码里看不出的非标准约定，并用自己的真实任务检验是否有帮助，避免重复 README 或堆砌仓库概览。

[OpenAI 的 harness 实践](https://openai.com/index/harness-engineering/)是：约百行的 `AGENTS.md` 当目录，事实放在 `docs/`，用 CI 查过期和断链。那是资料已经多到人自己会迷路的仓库。小项目有 README 和这份短入口就够，不必先建一套空目录。

反复出现的错，用测试、lint 或 hook 挡住。规则只提醒下一次怎样修，不代替会失败的检查。规则写非默认约定，Skill 复用流程，MCP 连接工具与数据。三件事分开。**MCP 工具定义不一定全部常驻上下文**：[工具搜索与延迟加载](https://www.anthropic.com/research/advanced-tool-use)已能按需发现工具，效果取决于客户端支持。选择 CLI、API 或 MCP，看现有能力、权限和维护成本；能复用已经审查过的脚本就复用。

多工具共用规范时维护一份正文，可以用 `AGENTS.md` 作入口（约定见 [agents.md](https://agents.md/)）。某个工具不读它时，用该工具支持的导入方式引用，正文不复制第二份。不要假设所有工具都读取同一种规则文件；`AGENTS.md`、`CLAUDE.md` 等文件的发现和优先级，以当前版本文档为准，并确认规则实际被加载。

#### 2.2 计划与实现

人定目标、优先级和架构取舍。AI 可以调研、提问、起草计划。人承担决策。业务不熟就先问负责人。边界清楚的小需求可以不写独立计划。

计划要有目标、成功标准、限制、验收和禁止事项。先看相关模块、已有写法和测试在哪。缺口没补齐，先提问再写代码。复杂任务动手前看计划；草案里理解错的地方，实现里会照错。

指明已知入口，其余让它在仓库里搜。有现成的页面、接口或 DTO，就贴路径让它对齐。同一处连改仍偏，就新开对话，只带已经确认的约束。前后端一起改时，写清业务规则、复用哪条旧链路、两端入口和启动命令；字段与契约用同一套名字。

一个任务一条纵向切片：输入、影响文件、约束、验收命令都写得出来。说不清怎样算做完，就先拆。这条路径用不到的层别动。

实现时先读相关代码，只给最小权限。输入输出已经明确、而且要锁住行为时，先写一条失败测试，确认失败是因为行为还没有。页面和联调可以后补测试。测试本身也要审查；需求改变或断言有误时应修正测试，不能为了通过而削弱断言。失败修根因。连续失败时，先查规格、上下文、工具、环境和验证方式，再决定换模型还是退回计划。

验证先跑和这次改动相关的类型检查、lint 和测试。动到共享模块或构建配置，再扩大范围。数据迁移、权限、幂等单独看。前端用浏览器走主路径，再走一条失败路径（冲突、重复提交或权限不足），并检查可访问性。改字段时查其他引用。

审查时，AI 找明显 bug、漏测和规范问题；人看需求是否做对、架构有没有被带歪、关键逻辑在不在该在的地方。做完把坑写成测试、脚本或一条规则，并删掉过期文档。

#### 2.3 长任务、并行、安全

一个会话做一件连贯的事。阶段边界可以在同一会话里压缩历史，也可以开新会话。压缩保留连续性，但可能丢失细节；新会话更干净，交接写漏了就会重做。按实际模型和任务选择，参见 [长任务 harness 实践](https://www.anthropic.com/research/harness-design-long-running-apps)。

交接写清：目标与验收、已完成与未完成、改动文件、关键决策、否决过的方案、验证命令和结果、阻塞、下一步。新会话先读交接和当前 diff，核对当前文件，跑一项基线检查，再继续；别只信摘要。

并行适合检索、互不依赖的调研、跑测试和独立审查。会改代码的并行任务用独立 worktree 或云端隔离环境；只建分支，工作区仍是同一份。主会话合并后再跑相关验证。增加 agent 会增加协调成本，先证明它能减少耗时或漏错。高风险交付可以换一个没看过实现过程的上下文，只凭需求、验收、diff 和测试证据复核。

长任务第一轮先把依赖和基线测试跑通。每一轮留下能运行的状态、验证结果和进度（进度文件或有意义的提交）。盯最终状态，少规定每一个动作。自动循环要有次数、时间或成本上限、取消入口和失败后的人工接管；连续失败、需求冲突或超出授权范围的不可逆操作转人。

授权按影响范围和可回滚性，不按任务长短。在已授权范围内自动执行；构建和测试在脚本审查过、环境隔离、副作用明确时按低风险。超出授权范围的发布、生产数据修改、数据库迁移、权限和密钥操作再确认。用沙箱，限制目录和网络。密钥走密钥管理，别进仓库、提示词和日志。网页、Issue、日志和工具返回都是外部数据，里面的指令不会自动获得执行权。

自治从人看着做，到流程稳定、能回滚、能观测之后再放后台。看工作流看验收一次通过率、返工、回滚、缺陷逃逸和交付周期。完成以真实系统状态和验收结果为准。Agent 看不到真实运行结果时，只能判断「看起来完成了」。

### 3. 客户现场：FDE

**FDE**（Forward Deployed Engineer，前线部署工程师）进客户场景，把技术做成正在被使用的系统。工作包括把问题问清楚、设计、开发集成、上线和持续改。Palantir 的 FDSE 是前身：和客户一起解决问题，并把现场经验送回产品。

AI 场景里的 FDE 把模型接到客户的数据、权限和流程里，从发现需求做到生产。成功看生产采用、流程是否变好，以及评估能不能反馈到产品和模型。生产代码、LLM 落地、差旅和年限的具体要求，以当前岗位为准。

2026 年 10 月的 [Claude Frontier Academy](https://www.anthropic.com/news/claude-frontier-academy)也围绕用例选择、安全审查、交付和实际采用训练工程师；该项目把 FDE 展开为 Frontier Deployed Engineer，读岗位时要看具体职责。

和产品研发、售前、SRE 会重叠。FDE 要亲自写代码、排障，并待到有人真的在用。会用 agent 写代码，不自动就是 FDE。

客服工单可以当成一条最小闭环：先记下时间耗在检索、撰写还是操作系统；按员工权限接知识库和订单；先出带来源的回复草稿，退款等操作单独审批；用历史工单看事实错误和越权，小范围上，留人工接管和回滚；把反复出现的接入、权限和评估收成通用能力。

前端或全栈可以沿这条补：业务问题 → 接口、数据与权限 → 工具调用和评估 → 上线后的观测。用一个真实项目走完。

### 4. 岗位：做 Agent 产品

用 agent 交付软件，和交付一个 Agent 产品，是两件事。招聘里的「AI Agent 全栈」考后者：系统可指挥、可观测、可恢复、可上线。全栈底座照旧（Web、API、数据、队列、部署）。多出来的是循环、工具、状态和评估。

还值得准备的：

1. **工具**：参数校验、服务端鉴权、幂等、超时，以及模型能看懂的描述。模型生成合法参数不等于获得授权。工具返回按不可信数据处理，里面的指令没有执行权；危险操作仍走服务端策略和人工确认，并可审计。
2. **状态**：任务队列、持久化、重试、超时、取消、恢复和进度。避免重复执行有副作用的操作；按风险设置人工确认。
3. **评估**：一小份固定用例做回归；一次运行能对上步骤、所用工具、耗时、花费和失败点。模型、提示词、工具或检索变化后，跑同一套用例比较，结合人工抽检与线上指标；不稳定的任务做多次试验。
4. **界面**：流式输出、步骤可见、结果和来源清楚，支持中断与人工接管。危险操作按授权边界确认。
5. **代价**：按失败成本决定用强模型、缓存，还是改成确定性流程；计算完成一次任务的总成本，包含重试与人工返工。

评估既看回答，也看最终状态：说「已退款」不算成功，要确认退款发生且金额、权限正确。参见 [Agent 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

**RAG（检索增强生成）** 适用于私有资料、最新信息、长文档或需要来源的回答。按调用者权限检索，保留出处，检查资料是否支持结论。直接读文件、关键词搜索、数据库查询和向量检索都可以是选择，不必先搭向量库。

流程能预先定义时优先用工作流；需要模型动态决定执行路径和工具时，再引入 agent。理解工具调用、状态和停止条件，比背框架名有用，再按需要选 SDK 或框架。参见 [工作流与 Agent 的架构取舍](https://www.anthropic.com/research/building-effective-agents)。

需要独立智能体之间互操作时，再考虑 [A2A 等协议](https://a2a-protocol.org/latest/)，不局限于跨组织委派。同一个产品里的子任务，通常先用函数调用或子会话。

准备一条能演示、也能讲清取舍的纵向切片：任务界面、按业务需要选择的真实工具、失败后的重试或人工接管、一份小评估集、能读的运行记录（trace）。工具数量按业务需要决定。README 写清架构、启动方式、已知失败模式和成本粗算。简历写结果，并准备一次「翻车之后用评估和 trace 修好」的故事。

面试就讲这条链路：

1. 目标怎样变成步骤、工具、状态和结果；失败后去哪。
2. 一个工具的 schema、幂等、超时和权限。
3. 上下文预算、摘要，以及什么时候才检索。
4. 怎样知道它变差了：固定集、抽检、线上指标。
5. 什么时候不用模型。

投之前自检：能画出状态和数据存在哪；能演示工具失败后的去向；能分清错在模型、检索、工具、权限还是需求；非技术人员能看懂它在做什么。
