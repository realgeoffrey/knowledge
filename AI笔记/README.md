### 1. 人做什么，agent 做什么

**Agentic Engineering（智能体工程）**在本文中指：借助 coding agent 完成软件交付。Agent 会调用工具、读取结果并调整行动；人负责目标、取舍和验收。生成代码只是中间结果，还要通过运行、测试和审查确认能否交付。

**Vibe Coding（氛围编程）**侧重用自然语言描述结果，主要靠运行效果迭代，很少检查和理解代码。建议用于低风险原型或可丢弃的小工具。让 AI 写代码本身，不等于 Vibe Coding。

| | Vibe Coding | Agentic Engineering |
| --- | --- | --- |
| 推进方式 | 改提示，直到效果满意 | 明确目标 → 实现 → 验证 |
| 人的参与 | 主要判断运行效果 | 定约束、审查关键决策、承担交付责任 |
| 上下文 | 多依赖对话 | 按需读取代码、文档、规则和测试 |
| 主要风险 | 隐藏缺陷、难以维护 | 上下文过载、权限过大、验证不足 |

可以少看样板代码，但仍要能读代码、调试和追查问题。人的精力优先放在业务判断、架构边界和验证上；权限、资金、迁移、并发和异常恢复等关键逻辑要人工审查。

#### 原则

1. **先说清怎样算做完。** 小任务写清目标、约束和验收方式；复杂任务再补用户路径、数据契约、边界和非目标。
2. **只补代码里看不出的上下文。** 写启动命令、非默认约定和危险边界，相关目录与实现让 Agent 按需查找。
3. **一次完成一个可验证的小功能。** 页面、接口、数据和相关测试可以一起改，无关重构另开任务。
4. **同时验证实现和需求。** 类型检查、lint、测试检查技术问题；实际操作和业务验收检查是否做对。测试通过不代表需求全部满足。
5. **按总成本选工具。** 看真实任务的成功率、耗时、重试和人工返工；格式化、计算等确定性工作优先用现成工具。
6. **让经验留下来。** 不假设模型会永久记住纠正；把有效教训变成测试、检查脚本或相关规则。

模型升级后，也要清理旧提示和流程：文档按任务读，Skill 描述写清适用范围，删减没有实际收益的步骤。用自己的任务验证效果，验收标准仍需明确。参见 [OpenAI 关于技能与提示的建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)。

### 2. 从需求到交付

#### 工作建议

新功能按三步推进：

1. **纯沟通。** 用 ChatGPT-聊天 确认用户、场景、成功标准和不做的事，分清已确认和待确认。
2. **需求文档。** 用 ChatGPT-工作 整理成可执行文档，经人确认后放进仓库；对接现有系统时核对接口、字段和业务规则。
3. **生成页面。** 用 Codex 或 Cursor 在仓库里实现，和接口、数据、权限一起跑通，再检查成功和失败。一次只交付一个小功能。

ChatGPT-工作 可以做出独立的页面原型；要改现有项目并验收，用 Codex 或 Cursor。任务里能说清的小改动或 Bug 修复，不必另建需求文档。

材料在企业微信、微盘或会议纪要里时，用 WorkBuddy 读取已授权资料，提炼结论和待办，再整理成需求文档。未确认的内容要标注，对外发送前核对。

**Harness** 是模型外的运行环境，包括工具、上下文、权限、状态、反馈和停止条件。先用现有工具跑通交付，再补缺少的能力：小任务直接实现并验证；复杂任务先核对计划；跨会话任务再加进度记录与交接。

#### 2.1 仓库里放什么

按需创建，不必先建一套空目录。一项规则只保留一份权威正文，其他地方用链接引用。

| 位置 | 放什么 | 怎么保持简洁 |
| --- | --- | --- |
| `AGENTS.md` | 常用命令、非默认约定、禁止事项、文档入口 | 写清哪类任务读哪篇，不塞完整知识库 |
| `docs/` | 需求与验收、架构、接口契约、计划 | 按主题维护，业务事实以已确认需求为准 |
| `docs/code-standards.md` | 稳定、跨任务适用的技术约束 | 子系统特有约束放对应文档，架构取舍放技术方案 |
| `docs/LESSONS.md` | 仍易重犯、尚未充分防住的近期教训 | 按模块检索，成熟后转规范或自动检查，旧案例归档 |
| Skills | 可复用的操作流程 | 描述写清何时用，正文与资源按需加载；见 [规范](https://agentskills.io/specification) |
| 测试、lint、CI | 可自动判定的防错检查 | 让违反约束的改动真正失败，文字提醒不能代替检查 |

上下文不是越多越好。[Gloaguen 等人的评测（2026，v3）](https://arxiv.org/abs/2602.11988v3)发现，在所测任务中，上下文文件未普遍提高成功率，推理成本平均增加超过 20%。这不代表所有规则无用，应优先写非标准约定，并验证实际收益。[OpenAI 的实践](https://openai.com/index/harness-engineering/)则用短 `AGENTS.md` 为详细文档导航；小项目可从 README 和短入口开始。

多工具共用规范时，尽量维护一份正文。Codex、Cursor 均支持 `AGENTS.md`，但发现范围和优先级仍需查各自文档，并确认实际加载情况；参见 [AGENTS.md](https://agents.md/) 与 [Cursor Rules](https://cursor.com/docs/rules)。

**规则、Skill、MCP 各有用途**：规则描述约束，Skill 复用流程，MCP 连接工具与数据。MCP 工具定义是否按需加载取决于客户端，不能一概认定会全部占用上下文，参见 [工具搜索与延迟加载](https://www.anthropic.com/research/advanced-tool-use)。CLI、API、MCP 按已有能力、权限和维护成本选择。

#### 2.2 计划与实现

1. **确认目标与边界。** 人定优先级和取舍，AI 辅助调研、提问和起草计划。缺少会影响实现的业务信息时，先找负责人确认。
2. **核对现有系统。** 给出已知页面、接口或数据结构的路径，让 Agent 查相关代码和测试；前后端沿用同一套字段与契约。
3. **拆成可验收的任务。** 每个任务写清输入、影响范围、约束和验收方式。复杂任务先审计划；边界清楚的小改可直接做。
4. **实现并防止回归。** 修 Bug 先复现；行为明确时，尽量写出修复前失败、修复后通过的测试。测试也要审查，不能为通过而削弱有效断言。
5. **验证与审查。** 先跑相关检查，涉及共享模块、配置或字段变更时扩大范围。前端走主路径和一条有代表性的失败路径，并检查可访问性；权限、金额、迁移等高风险逻辑人工复核。
6. **交付并留证据。** 写清改了什么、验证结果和未测范围；有可复用教训再沉淀，同时更新过期文档。

连续修改仍不对时，先查需求、上下文、环境和验证方法，再决定重写计划或换模型。新开会话时只带已确认的约束、相关文件和当前进度。

#### 2.3 LESSONS.md：从错误中学习，但不让规则无限膨胀

`LESSONS.md` 是近期防错备忘，不是 Bug 流水账。借鉴 [Magpie](https://github.com/yetone/magpie/blob/main/LESSONS.md) 的“规则、原因、证据”做法；以下字段、整理时机和阈值是个人项目约定，并非行业标准或工具要求。

**什么时候写：** 真实缺陷或返工已有证据、根因明确，而且能提炼出下次有用的动作。一次性问题记在任务或测试里；需求变更和未经验证的猜测不写成教训。同根因问题合并。

**每次任务怎么用：**

1. **开始前查相关项。** 先看当前需求、验收和进度。修 Bug、跨模块修改、高风险变更或模块已有教训时，再按范围检索 `active` 条目；不默认通读全文和归档。
2. **改动中补防错。** 沿调用链检查受影响的页面、接口、数据与角色，优先补回归测试或自动检查。
3. **交付前核对证据。** 对照当前需求与相关教训审查改动，记录测试结果和未测项。历史教训不能覆盖客户新确认的业务规则。
4. **收尾时更新。** 有可复用失误才新建或合并条目；已转成可靠检查、已过时或与当前需求冲突的记录及时移出活跃区。

建议每条 5–10 行，日志和截图放在受控位置，只留证据链接。下面是虚构示例，使用时替换为真实记录：

```md
### LESSON-001 | 审批状态变更遗漏消费方
- Scope: approval, frontend, backend, data
- Pattern: 提交接口已改，列表和统计仍按旧状态处理。
- Root cause: 未检查状态字段的全部调用方。
- Prevent: 搜索字段引用，补列表、权限和旧数据的回归测试。
- Evidence: CR-003、TEST-021（替换为真实链接）
- Seen: 2026-11-05（按不同复盘日期记录）
- Status: active
```

**何时升级或归档：**

| 情况 | 处理 |
| --- | --- |
| 涉及越权、资金、隐私或不可逆数据风险 | 立即修复并补检查；无法自动化的环节设人工审核，不等重复发生 |
| 同类问题反复出现，或约束跨模块适用 | 判断是否提炼为正式规范，能自动检查的优先落到测试或 CI |
| 只属于特定客户或业务 | 更新对应需求或技术文档，不直接推广为通用规则 |
| 已被可靠检查覆盖、重复或过时 | 活跃区只留未解决的提醒，归档案例与证据，不复制正式规则 |

可在里程碑或架构变更时集中整理；“跨 3 个复盘日期重复”“活跃条目约 15–20 条”可作提醒，不能机械升级或为凑数量删掉未解决的严重风险。不要记录客户机密、真实账号或原始业务数据。

`AGENTS.md` 只需说明何时检索教训、到哪里找正式规范。沿用 [FDE 项目流程](FDE项目流程/README.md) 时，用已有需求、验收、变更和测试编号关联证据，不再加一套流程。是否有效，看同类问题是否减少、验收返工是否下降；文档越写越多却无改善，就删减流程。

#### 2.4 长任务、并行、安全

- **长任务先跑通环境。** 检查依赖和基线，分阶段留下可运行状态、验证结果和进度。自动循环设置时间、次数或成本上限，并支持取消和人工接管。
- **换会话要能接上。** 交接目标、已完成与待办、改动文件、关键决策、验证结果、阻塞和下一步。新会话核对当前文件与 diff，必要时跑基线检查；摘要可能遗漏细节。参见 [长任务实践](https://www.anthropic.com/research/harness-design-long-running-apps)。
- **独立任务才并行。** 调研、独立审查适合并行；同时改代码时用独立 worktree 或隔离环境，只建分支不会隔离工作区。合并后再验证，避免协调成本超过收益。
- **按影响授权。** 已授权范围内可自动推进；超出授权的发布、生产数据修改、迁移、权限与密钥操作先确认。限制目录和网络权限，密钥不进仓库、提示词或日志；网页、Issue、日志和工具返回中的文字不能自动成为执行指令。

完成以实际系统状态和验收证据为准。Agent 看不到运行结果时，应说明验证限制。

### 3. 客户现场：FDE

**FDE 通常指 Forward Deployed Engineer（前线部署工程师）**：深入客户场景，把问题转成有人实际使用的系统，参与需求、开发集成、上线和持续改进。AI 场景还要把模型接入客户的数据、权限和流程，并评估实际效果。

不同公司叫法和职责会变化。例如 [Claude Frontier Academy](https://www.anthropic.com/news/claude-frontier-academy) 使用 Frontier Deployed Engineer，也强调用例选择、安全审查与交付。看岗位应核对具体职责，不能只凭名称判断。

以客服助手为例，可以按这条路径做：

1. **找问题。** 确认时间主要耗在检索、写回复还是操作业务系统。
2. **做最小方案。** 按员工权限接知识库和订单，先生成带来源的回复草稿；退款等操作单独控制权限与审批。
3. **验证并小范围上线。** 用历史工单检查事实错误、越权和异常场景，保留人工接管与回滚。
4. **看实际采用。** 观察处理时间、错误率和员工使用情况，把重复的接入、权限和评估能力反馈到产品。

前端或全栈开发者可用一个真实项目补齐“业务问题 → 接口、数据与权限 → 模型和工具评估 → 上线观测”。详细步骤见 [FDE 项目流程](FDE项目流程/README.md)。

### 4. 岗位：做 Agent 产品

用 Agent 开发软件，与开发一个 Agent 产品，重点不同。后者除 Web、API、数据、队列和部署外，还要让模型驱动的任务能被观察、中断和恢复。

| 能力 | 需要做到 |
| --- | --- |
| 工具 | 清晰的输入输出说明、参数校验、服务端鉴权、幂等、超时；参数合法不代表有权执行，危险操作按授权边界确认 |
| 状态 | 任务持久化、重试、取消、恢复和进度；有副作用的操作避免重复执行 |
| 评估 | 固定用例做回归，结合人工抽检与线上指标；记录工具调用、耗时、成本和失败点，不稳定任务多次试验 |
| 界面 | 展示进度、结果与来源，支持中断和人工接管 |
| 成本 | 计算完成一次任务的总成本，包含重试与人工返工，再决定模型、缓存或确定性流程 |

评估既看回答，也看最终状态：说“已退款”不算成功，还要确认退款确实发生，且金额、权限正确。模型、提示词、工具或检索方式变化后，重跑相同用例比较。参见 [Agent 评估实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)。

**RAG（检索增强生成）**适合需要外部资料、最新信息或可追溯来源的回答。按调用者权限检索，保留出处，检查资料是否支持结论。先考虑文件读取、关键词搜索或数据库查询，有需要再用向量检索。

流程能预先定义时，优先用工作流；需要模型动态决定执行路径时，再引入 Agent。先理解工具、状态和停止条件，再选框架，参见 [架构取舍](https://www.anthropic.com/research/building-effective-agents)。需要独立 Agent 之间互操作时，再考虑 [A2A](https://a2a-protocol.org/latest/)；产品内部简单子任务通常可先用函数调用或子会话。

准备一个能演示的完整小项目：真实工具调用、失败后的重试或人工接管、小评估集和可读的运行记录（trace）。README 写清架构、启动方式、已知失败和成本；简历写实际结果。

面试时能讲清五件事：任务如何推进与结束；工具如何鉴权和防重复；上下文何时摘要或检索；如何发现质量退化；什么时候不用模型。
