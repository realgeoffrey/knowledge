# Agent 开发学习计划

> 面向：有编程基础、没做过 Agent 开发的初学者
> 目标：约 14 周，从"会调 API"走到"能交付一个带评测、可观测、能上线的小 Agent"
> 用法：按阶段推进，**每个阶段必须产出一个能运行的东西**。读完不算学会，跑起来才算。

## 一、开始之前：三条原则

1. **先手写，再用框架。** 前两个阶段别碰 LangChain。用官方 SDK 把对话循环、工具调用循环亲手写一遍。框架解决的是你已经痛苦过的问题，没痛苦过就用框架，只会把问题藏起来。
2. **每阶段一个可运行产物。** 没有跑起来的东西等于没学。宁可学得慢，也要每阶段有个能演示的 demo。
3. **先评测，再优化。** 从阶段 3 起，任何"我觉得这样更好"的改动，都要先有 20 条测试用例。没有评测的调优是玄学。

## 三、各阶段详解

### 阶段 0：地基（第 1 周）

**要学的知识**

- token 是什么、中英文 token 数量差异、如何估算成本和上下文占用
- 上下文窗口、输入/输出计费、模型的上下文上限
- `temperature` / `top_p` 对输出的实际影响（动手对比，不要只记定义）
- 流式响应（SSE）的原理
- HTTP 客户端的超时、重试、错误码处理

**动手练习**

- [ ] 用官方 SDK（OpenAI 或 Anthropic，选一个即可）写一个命令行多轮对话
- [ ] 每次请求打印 `input_tokens` / `output_tokens` / 本次花费
- [ ] 打开流式输出，逐字打印
- [ ] 故意塞一段超长文本，观察报错，写一个自动截断或摘要的逻辑
- [ ] 加超时 + 指数退避重试

**验收标准**：断网、超时、超长输入、限流四种情况下程序都不崩溃，且给出可读的错误提示。

---

### 阶段 1：提示与结构化输出（第 2 周）

**要学的知识**

- 消息角色：system / user / assistant，以及各自适合放什么
- few-shot 示例的写法与适用场景
- 结构化输出：JSON mode、JSON Schema 约束、function calling 做抽取
- 输出解析失败的兜底策略（重试、修复、降级）
- prompt 版本管理（为什么要把 prompt 当代码管）

**动手练习**

- [ ] 写一个"文本 → 固定 JSON"的抽取器，比如把一段简历或论文摘要抽成 10 个字段
- [ ] 用 schema 强约束输出，禁止模型自由发挥
- [ ] 准备 20 条测试样本，统计成功率，记录失败案例的共同点
- [ ] 加"解析失败自动重试一次 + 仍失败则降级"的逻辑
- [ ] 准备 3 个 prompt 版本，在同一测试集上对比，记录分数

**验收标准**：20 条样本成功率 ≥ 95%；失败时能说清是模型能力问题还是你的 schema 设计问题。

---

### 阶段 2：工具调用与 Agent 循环（第 3–4 周）

**要学的知识**

- 工具调用流程：发送工具定义，读取模型请求的工具和参数，执行后按调用 ID 回传结果。OpenAI Responses 用 `function_call` 的 `call_id` 关联 `function_call_output`；Anthropic Messages 用 `tool_result.tool_use_id` 对应 `tool_use.id`。[OpenAI 示例](https://developers.openai.com/api/docs/guides/function-calling) · [Anthropic 示例](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- ReAct 循环：思考 → 调工具 → 观察 → 再思考
- 上下文增长的规律与压缩策略（摘要、裁剪、只保留关键结果）
- 工具设计的三个原则：**描述写清楚、参数尽量少、返回尽量精简**
- 循环控制：最大轮数、超时、死循环检测

**动手练习**

- [ ] **不借助任何框架**，手写完整 Agent 循环，给它两个工具：计算器、获取当前时间
- [ ] 问一个需要 3 步以上的问题，记录每轮的工具名、参数、返回值和最终答复。用这份记录说明哪一步用到了前一步的结果。
- [ ] 让工具故意返回错误（比如除零、文件不存在），观察模型是否重试或换路径
- [ ] 加最大轮数限制、单步超时、重复调用检测
- [ ] 记录每轮 token 消耗，画出增长曲线，理解为什么长任务会爆上下文

**验收标准**：能完成至少 3 个多步任务；构造一个死循环场景，程序能自己停下来。

---

### 阶段 3：RAG 知识库（第 5–6 周）

**要学的知识**

- 切片策略：固定长度、按标题/段落结构切、重叠窗口
- embedding 模型的选择与维度，**建库和查询必须用同一个模型**
- 向量库：Chroma / LanceDB / pgvector，先会用一个就够
- 相似度、top-k、混合检索（向量 + 关键词）、rerank
- 引用溯源：回答里标出文件名和行号
- 检索评测：recall@k，怎么构造"问题 → 标准答案所在段落"的测试集

**动手练习**

- [ ] 拿自己 20–50 篇笔记或 Markdown 文档建库
- [ ] 三种切片策略各建一个库，用同样的问题对比召回效果
- [ ] 做 20 条问题的评测集，算 recall@3、recall@5
- [ ] 加 rerank，对比提升幅度
- [ ] 输出必须带引用（文件名 + 行号），点开能核对原文
- [ ] 专门测试"库里没有答案"的问题，要求模型拒答而不是硬编

**验收标准**：20 条问题 recall@5 ≥ 80%；无答案问题能正确拒答；每个回答都能追溯到原文。

> 这块最容易自我欺骗："回答看起来不错"不等于检索对了。一定要看检索出来的原文段落。

---

### 阶段 4：MCP（第 7 周）

**要学的知识**

- MCP 的架构：host / client / server 三层
- 三种能力：tools（可调用）、resources（可读取）、prompts（预置模板）
- 传输方式：本地子进程可通过 stdio 通信，远程服务可用 Streamable HTTP，响应可按需通过 SSE 流式返回。[MCP 传输规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)
- 权限与安全：server 能做什么，取决于你给它的权限

**动手练习**

- [ ] 用自己的 Agent 接一个现成 MCP server（比如 filesystem 或 fetch），成功调用
- [ ] 自己写一个 MCP server，暴露"搜索本地 Markdown"能力
- [ ] 同时挂 2–3 个 server，观察模型如何在工具间选择
- [ ] 用一份内存中的模拟文件清单练习删除操作。工具先展示拟删除的条目，只有条目在白名单内且用户确认后才从清单移除。分别验证允许、拒绝和取消三种结果。

**验收标准**：自己的 server 能被官方客户端（如 Claude Desktop）或你的 Agent 成功调用；能说清"接入第三方 server 前要先看什么"。

---

### 阶段 5：架构模式（第 8–9 周）

**要学的知识**

- workflow 五种模式：链式、路由、并行、编排者-工人、评估者-优化者
- Agent 的适用边界：**任务路径不可预先确定时才用 Agent**
- 状态机思路（LangGraph 的设计哲学）
- 多智能体：知道存在即可，先别用

**动手练习**

- [ ] 选一个真实任务，比如"调研一个主题并写 500 字摘要"
- [ ] 用纯 Agent 实现一版（模型自己决定查什么、查几次）
- [ ] 用 workflow 实现一版（固定：路由 → 并行查 3 个来源 → 汇总 → 校对）
- [ ] 两版对比：成功率、延迟、成本、调试难度
- [ ] 读 [12-Factor Agents](https://github.com/humanlayer/12-factor-agents)，写 3 条自己的体会

**验收标准**：能说清在什么条件下该用哪种方案，而不是默认"Agent 更先进"。

---

### 阶段 6：评测与可观测（第 10–11 周）

**要学的知识**

- 评测集设计：正常用例、边界用例、对抗用例各占多少
- 三种评分方式：代码判定、LLM 当裁判、人工标注，各自适用场景
- trace：一次请求的完整链路、工具调用、token、耗时
- 回归测试：每次改 prompt 或换模型都要重跑
- 怎么让 LLM-as-judge 与人工判断对齐

**动手练习**

- [ ] 接一个可观测工具（Langfuse 或 OpenTelemetry + 自建面板）
- [ ] 从阶段 3 的 20 条用例出发，补充至少 10 条用例（包括边界情况），为每条写下参考答案或判分标准。做成一条命令跑完并输出分数。
- [ ] 加 LLM-as-judge，抽 30 条和人工标注对比，看一致率
- [ ] 改一个 prompt，跑评测，记录"变好还是变差，差多少"
- [ ] 把评测接进 CI，改动时自动跑

**验收标准**：面对"这次改动效果如何"能给出数字答案，而不是"感觉好多了"。

---

### 阶段 7：生产化（第 12–14 周）

**要学的知识**

- 容器化、环境变量、密钥不进代码库
- 限流、成本上限、熔断
- prompt injection 攻击面与防御
- 工具权限最小化、敏感操作二次确认、沙箱执行
- 灰度发布与回滚、日志与告警

**动手练习**

- [ ] Docker 打包，部署到仅自己可访问的低成本测试环境（VPS 或 serverless）
- [ ] 开放给其他用户前，验证每日 token 上限与单用户限流均能拒绝超额请求
- [ ] 构造 prompt injection 攻击（诱导它泄露 system prompt、执行越权工具），测试并修复
- [ ] 加健康检查、错误告警、关键指标看板
- [ ] 写一份 README：怎么跑、怎么测、已知限制

**验收标准**：连续跑一周不崩；账单可控；别人拿到仓库能按 README 跑起来。

## 四、贯穿全程的练习项目

只学不练会忘，建议用三个项目串起所有阶段：

| 项目 | 交付阶段 | 做什么 | 练到什么 |
| --- | --- | --- | --- |
| **A. 个人知识助手** | 阶段 3 | 用你自己的笔记做 RAG 问答，带引用 | 切片、embedding、检索评测、拒答 |
| **B. 网页调研 Agent** | 阶段 5 | 输入主题，自动搜索、抓取、汇总成报告 | 工具调用、循环控制、workflow 设计 |
| **C. 真实场景小工具** | 阶段 7 | 解决你自己或身边人一个真实痛点 | 评测、可观测、部署、安全 |

**强烈建议**：项目 C 一定要选"你真的会用"的场景。为交付而做的项目，和为了练习而做的项目，遇到问题的深度完全不一样。

## 五、每周节奏

| 时间 | 做什么 |
| --- | --- |
| 周一至周四 | 每天 1–2 小时：读概念 + 写代码，小步提交 |
| 周五 | 复盘：整理笔记、补测试、记录踩坑 |
| 周末 | 推进练习项目，做本周验收 |

**一个反直觉的建议**：每周留半天**重读自己的旧代码**。Agent 项目的坑多半藏在"当时没想清楚"的地方，隔一周再看会很明显。

## 六、避坑清单

1. **别一上来学框架。** 先把循环手写一遍，否则框架一报错你完全无从下手。
2. **别做多智能体。** 延迟翻倍、成本翻倍、错误叠加，且极难调试。单人项目 95% 的场景不需要。
3. **别在没有评测的情况下调 prompt。** 改了 A 场景好了 B 场景崩了，你根本发现不了。
4. **别把整本书塞进上下文。** 贵、慢、且模型抓不住重点。先检索再喂。
5. **别不看 trace 就猜 bug。** 打印完整消息链，问题往往一眼可见。
6. **别用超长 system prompt 解决一切。** 规则越多，模型越容易顾此失彼；能写进代码约束的就别写进提示词。
7. **别忽视成本。** 开发阶段就记录花费，否则上线第一天可能被账单吓到。
8. **别追新框架。** 每月都有新东西，先把上下文管理、评测、工程化这三件不变的事做扎实。

## 附：怎么判断自己真的入门了

能独立回答下面这些问题，就算过了初学者阶段：

1. 为什么同样的问题，两次回答不一样？你能控制到多大程度？
2. 一个 Agent 卡住了，你怎么判断是模型能力不足、工具描述不清，还是上下文太长？
3. 你的 RAG 检索准不准？有数字吗？换 embedding 模型会怎样？
4. 这次改 prompt 的效果提升，是真的还是错觉？
5. 线上跑一天要花多少钱？超了怎么办？
6. 什么情况下你会选择 workflow 而不是 Agent？为什么？
