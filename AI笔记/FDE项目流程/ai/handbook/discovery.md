# 需求与原型：G1 / G2

> AI维护，按任务读取。业务规则写 [需求](../specs/requirements.md)，批准与固定版本写 [验收记录](../records/acceptance.md)；阶段顺序见 [八步流程](../../README.md#八步流程)。

## 1. 用真实案例访谈

先明确目标、本期边界、确认人与交付约定，请客户演示最近一笔正常业务和一笔异常业务。

| 追问 | 产出 |
| --- | --- |
| 哪里费时、易错？怎样算解决？ | 现状、目标、验收场景 |
| 谁发起、信息从哪来、交给谁、怎样结束？ | 角色、对象、交接、样本 |
| 办不下去怎么办？能撤回、驳回、重提吗？ | 状态、失败、补救规则 |
| 谁能看、改、审批？能审批自己吗？ | 操作、数据、字段范围及特殊限制 |
| 数字用于什么决定，按何口径和时间计算？ | 筛选、统计、导出规则 |
| 老数据怎样用？接口、账号和样本谁何时提供？ | 规模、清洗、兼容、依赖 |

只用获准材料并优先脱敏；转写、OCR、AI 摘要须核对。未知与争议进 [OPEN](../records/clarifications.md)，不猜答案。

## 2. 先建业务模型，再画菜单

按需求模板填写范围、字段、权限、状态表，详情引用共享规则。金额、日期、数量、审批和归属写明边界；菜单可见、动作可执行、记录可访问、敏感字段可见分别定义，不能只写“正常处理”“合理权限”。

## 3. 一条需求的最小写法

以下仅为虚构示例：

```text
REQ-001 提交采购申请（草稿，来源 MEET-001）
角色/目的：员工提交自己的草稿，交部门主管处理。
前置：已登录、有提交权限、部门已配置主管。
规则：事项、金额引用字段表；金额>0、最多两位小数。
成功：进入待主管审批，记录提交人/时间；不含下单、收货、付款。
失败：缺主管提示联系管理员，状态不变，无半条审批记录。
AC：合法提交只生成一次记录；非法金额拒绝且不写数据；
直接请求他人草稿被拒绝；重复提交不重复流转。
```

AC 用“已知条件→动作→可观察结果”覆盖正常、边界和失败。非功能要求写场景、指标、环境和方法：规模、响应时间、浏览器、导入失败、接口超时/重试等；数值由客户约定。

## 4. 会后只处理差异

保存/引用原件，标明位置、提炼去向及未处理部分；真实会议才建 MEET，普通反馈记已有事项。区分事实、客户决定、建议、未知，汇总新增、拟改、取消、未决项。

新增按 [语义匹配规则](../specs/requirements.md#需求索引) 查重并复用同义 REQ/AC。未确认草稿可迭代，改变已确认行为走 [CR](../changes/TEMPLATE.md)，不借新编号绕过批准；客户确认具体版本，AI 不代签。

## 5. 准备设计与离线原型

[设计规范](../specs/design.md) 保存唯一设计规则，[规范示意页](../prototypes/design-system.html) 与 [业务原型](../prototypes/pages/index.html) 分开。需求前可准备未批准基底，不虚构 REQ/AC/PAGE，不算 G2 通过。默认参考 RuoYi-Vue-Pro 的 Vue 3 + Element Plus 后台，实际工程在 G3 固定；大屏按需约定主题、字体、画布与验收条件，不直接放大后台。

只读适用设计章节/tokens、主题映射和相关 REQ/AC；正式页面另读方案中的工程与共享依赖。已批准项目用固定清单，不随模板升级。修改按 [设计维护步骤](../specs/design.md#修改与项目确认)，生成按 [静态页面规则](../prototypes/README.md#静态页面生成规则)，不复制规则。

用客户业务替换采购样例，输入角色/字段/状态、页面入口出口、正常与反例数据、待决定问题；未知保留，探索草图标待验证。

## 6. 按业务任务评审

[原型说明](../prototypes/README.md) 唯一维护 PAGE→REQ→场景、演示路径、模拟范围与未覆盖项。评审前检查离线打开、导航、适用的空态/错误/无权限/冲突、按钮原因、反馈和重置。模拟不证明后端权限、事务、并发或性能。

提供页面、需求/设计版本、场景和限制，按“提交业务→换处理角色→异常路径→查询记录”对照 AC 核对字段、单位、默认值、权限与遗漏。

意见及原话、场景、分类、决定、下一动作/期限和结果入口写验收记录；疑问关联 OPEN，业务变化走 CR，原型只链接。获采纳设计、原型及共享资源随需求组合固定；后续行为或已批准视觉承诺变化时同步相关规范与原型，内部重构无需重画。
