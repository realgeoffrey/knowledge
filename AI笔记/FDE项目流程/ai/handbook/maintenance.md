# 长期迭代与文档维护

> AI维护，按需执行。业务批准和需求复用分别以 [验收](../records/acceptance.md) 和 [需求](../specs/requirements.md) 为准。

流程版本：FDE1.5。项目采用来源与版本只记 [项目概况](../specs/project.md)，通用流程升级不改变业务 BL、原型版本或确认方式；同步前比较项目差异，保留既有约定和记录。

## 日期与迭代顺序

| 来源 / 用途 | 文件名与顺序 |
| --- | --- |
| 人提供的需求原件、原始录音录像、人工纪要、业务表格等 | 集中在来源目录，由人保留原名和原件。有日期区分需求时由人按已核实日期命名 |
| AI 整理的任务、访谈纪要、变更、验证记录 | `TASK-001-english-name.md`、`MEET-001-english-name.md`、`CR-001-english-name.md`、`RUN-001-english-name.md`；序号递增、项目内唯一，不因换日期/批次重置 |
| AI 阶段产物、截图或测试报告 | 沿用原型版本、PAGE/TEST/RUN 等可追溯编号作为前缀，正文或所关联记录标明生成日期；不另造日期序号 |
| AI 提炼的需求与验收条件 | 依已有 `REQ-001` / `AC-001-01` 标识关联和排序；现行汇总/模块规格保持稳定路径，不为增加文件名前缀复制一套需求 |

- 原件由人维护。AI 转写、OCR 和补充纪要保存在 `ai/meetings/`。在衍生文档记录原件路径、日期或适用版本及段落或时间点；若用收到日期区分，注明含义。
- 记录实际影响追溯的事件、确认或生效日期，新增日期沿用项目格式。未知标未知；需要区分同日顺序时用编号、版本、前序或已知时间。实质变化保留差异及决定依据。
- `README`、`AGENTS`、项目状态、现行规格与运行代码保持稳定路径，通过正文的日期/版本/变化记录迭代；同文件内 RUN/UAT 各自带日期。模板保留 `TEMPLATE.md` 和日期占位，框架已有代码/迁移命名规范优先沿用。
- 日期不代表批准或优先级，序号不代替有效 BL。已固定批准包不重命名；其他文件改名时保留编号、锚点、原名映射并修正链接，不改写历史确认或命令。

## 1. 何时检查，谁执行

本轮 AI 按实际变更选择动作，你核对业务与证据结论。

| 触发 | 动作 |
| --- | --- |
| 新资料/需求 | 核对并按实际变化更新[适用资料的位置与版本](../specs/project.md#原始资料位置)。查现行规则，可能复用旧规则或存在历史承诺时定点查归档；复用同义 REQ/AC，改变有效规则走 CR |
| 候选包批准 | 按验收记录核对完整组合、起点、批准映射与冲突；切换前重读当前 BL |
| 项目状态或可继续的动作变化 | 顶部只写当前结果、实际阻塞与下一步，日期按实际状态变化更新。工作详情和恢复检查点放在可展开区，已完成项退出当前工作。批准目标、当前实现及最近交付分别链接各自证据 |
| 入口、链接/锚点、编号定义、证据结构、原型登记或生成槽变化；交付前 | 运行 `python3 ai/scripts/check_context.py`；迁移用 `--check-file` 指定目标，脚本不证明业务正确或验收通过 |
| 模板规则或脚本维护 | 跑与改动相关的检查；改入口或跨文档规则用结构检查，改脚本补对应回归 |
| 历史妨碍定位、需移交或确有拆分需求 | 按下节处理相关范围，保持编号、链接及原始证据可定位 |

仅改文案或代码且未触及上述结构时，做与改动相称的验证。无法运行所需脚本时，说明未运行并人工核对能核对的部分。

## 2. 按职责拆分现行规格

已有结构能定位和维护就沿用。独立模块反复引发查找困难或并行修改冲突时再拆分；不按模块数量、行数或迭代机械切割。

- `ai/specs/requirements.md` 保留全局索引、术语、共享规则；模块唯一详情放 `ai/specs/requirements/<module>.md`，共享内容只引用。
- `ai/specs/solution.md` 保留工程、公共架构、命令与模块索引；独立方案放 `ai/specs/solutions/<module>.md`。
- 原型保留实际入口，不每期复制整套资料；候选/已批准版本由固定提交或评审包区分。

仅实际拆分时建目录。不改编号或业务含义；原入口显式保留被引用的锚点（含旧标题自动锚点）及转向，导航标题不以真实编号开头，编号定义只留目标。发现业务差异单独处理，不当排版调整带过。

## 3. 哪些历史可以移走

把还会用到的结论和依据写进现行文档。还需要查阅或移交的旧 AI 文档放入 `ai/archive/<scope>/`，保留类型和编号，重名时加版本。已经结束且没有后续用途的 AI 过程稿可以删除。

例如，把旧沟通草稿中已确认的结论写进需求，再删掉用完的草稿。如果要把这次整理提交到 Git，把「更新需求」和「删除旧草稿」一起提交就行。要保留的旧文件也可以移到归档目录，随这次改动一起提交。无需为了备份旧稿先单独提交一次。

现行入口必须保留：

- 当前有效 REQ/AC、当前 BL 及其继承/新增批准入口、当前 AC 状态与最新适用 RUN/UAT。
- 原编号、已被引用的标题/锚点、历史转向；旧阶段的范围、版本、结论索引。
- 待复验、未关闭缺陷、未完成轮次。

历史摘要或索引开始妨碍定位当前事项时，按范围合并历史入口，现行页只保留必要索引字段和原锚点短跳转。全量历史按编号或范围检索；已确认与取消的需求沿用原编号，保留决定依据。移除重复正文前先核对唯一记录及链接，原始材料、原获批包和批准证据原样保存。

## 4. 每次迁移按此顺序完成

1. 列出“原文件/编号/锚点→目标”，划出当前有效和仍在执行的内容。
2. 写目标并按新父目录修正正文相对链接，包括目标未移动但相对关系变化的报告。
3. 原位置显式保留旧锚点及转向，旧标题自动锚点也须保留；导航标题可写“已迁移：REQ-001”，不再以编号开头。跨阶段复用 BL 时链接原登记，不重复定义；不能用文件级跳转替代已引用片段。
4. 一次结构检查，用 `--check-file` 逐个指定迁移后的 AI 维护 Markdown；多目标重复传参，均相对项目根，默认检查仍包含现行资料。

```sh
python3 ai/scripts/check_context.py --check-file 'ai/archive/purchasing-phase-1/RUN-001.md' --check-file 'ai/archive/purchasing-phase-1/CR-001.md'
```

示例路径须换成真实目标。缺失、非 Markdown、项目外路径、来源资料或符号链接会失败，不能省掉失败文件后宣称通过。

5. 脚本检查本地目标、已读 Markdown 的 ATX 标题/显式锚点、现行编号标题、需求 AC 表及阶段 BL/FB/BUG 表首列和 UAT 条目的定义唯一性、追踪表“已验证”行的实现信息，以及落到本次已读 Markdown 的 BL/RUN 锚点、原型 HTML 登记及设计 token/版本。`sources/` 原件链接只查路径是否存在，正文与引用位置按任务核对。未读的 AI 历史记录可用 `--check-file` 单独检查。实现列按整格匹配缺失值，整格“未实现/未开始/未验证”不能标已验证；版本说明内的这些文字不拦截。代码示例、普通引用和指定历史不算现行定义。HTML 动态路由、其他 Markdown 语法/渲染器、业务结论、实现版本正确性与批准真实性仍需核对。
6. 归属或链接不明就保留原文或恢复。记录迁移映射和剩余项，已有 RUN 只链接；项目状态入口实际变化时更新。

## 5. 用这些场景验收维护结果

工具回归运行 `python3 -m unittest discover -s ai/scripts -p 'test_*.py'`：应发现断链/失效锚点、重复定义、已验证行缺引用、遗漏登记页面；指定一个历史不读其他历史，多目标逐个检查，项目外路径、来源资料和符号链接不能用作指定检查文件。为 REQ/TASK/CR/BL/RUN 等真实记录保留稳定显式锚点，改名仍保留；AC 可链接所属 REQ 的固定锚点。

另沿链接复核晚到批准的适用范围、同义需求编号复用、人工原件与 AI 衍生文档区分，以及模块拆分后原入口是否仍可定位。脚本不证明这些业务判断，AI 须展示依据。

### 流程变更的选用演练

规则实质改变时，挑受影响的场景走读或演练。比较效率时，在同一工具和模型内用相同输入与起始版本对比新旧流程，记录首次有效动作前的读取量、额外写入、耗时及验收遗漏。单测不代替业务演练，走读也不算实际运行。

| 起点与新输入 | 应观察到的结果 |
| --- | --- |
| 当前BL已前进，收到旧起点候选包批准 | 保留当前组合，核对差异/冲突与批准映射；冲突未补确认不切换 |
| 人补充原始需求或更正人工纪要 | 对照原始需求、现行《软件需求规格说明》和相关会议记录。按人的决定更新对应 REQ/AC 并引用出处。待拍板事项留待决定，改变已确认规则走 CR |
| 草稿有未说明细节，或实现时遇到真实阻塞 | 先选定可逆做法并给出结果供评审；实际无法推进时在对话问具体场景，答复写入相关 AI 规格后继续 |
| 两个模块同改一个AC，或规格拆分后继续开发 | 现行定义唯一，原锚点可定位；冲突显式处理，受影响AC待复验 |
| 一个功能已收尾，新会话只收到“继续” | 从项目状态找到有效版本及下一项已授权工作，有 TASK 再读其检查点；已完成项退出当前工作，必要的旧证据仍可按原编号定位 |
| 评审前原型小改；另测带新答复或共享依赖的变更 | 小改按原型入口接续；有新答复或共享影响时定点展开原话、规则与回归。用相同任务比较首次编辑前的读取量，核对版本、授权、验证和结果 |

## 并行工作

1. **定位影响**：实际阻塞时定位受影响 REQ/AC 和共享依赖。从接口、数据、权限、状态、字典、配置和外部依赖判断哪些工作可独立推进。
2. **选可做工作**：继续独立且已授权的部分，正式开发满足各自适用的 G1/G2/G3。需人回答的具体实现问题走 [执行入口](../../AGENTS.md#默认做法与实现阻塞)。
3. **保持承诺边界**：项目状态逐行指向各范围/阶段/AC，验收记录存正式结论。拆分、排除、延期原承诺须明确确认，改变已批准范围走 CR；不能自行圈“已确认子集”过关，G4/G5 仍覆盖被验范围全部有效 AC。未来问题不自动阻塞本期，但无影响须有依据。
4. **隔离写入、串行整合**：一个项目一个完整有效 BL。整合 AI 串行登记 REQ/AC/TASK/CR/BL/RUN 并回传编号；其他任务用临时号，不抢共享编号。分配独立路径/工作区；共享规格、项目状态、追踪/验收、接口由整合者重读再合并，保留其他行，不用旧快照覆盖。交接读文件/检查点，不靠聊天恢复，人的确认权不变。
5. **核对后生效**：重读当前 BL、共享文件、任务起点；旧起点合入期间已生效内容，冲突仅停依赖部分，批准按验收规则。记录合入代码版本，核对共享契约并做集成回归；旧 RUN/UAT 不自动代表新组合通过。失败保留现场，从最后已核实检查点恢复。

这些规则不提供锁或事务。无法保证写入归属、隔离和串行整合时改顺序执行，不要求人维护额外排程或锁台账。

## 启用和迁移模板

- 复制或合并模板后，在目标项目的目录里开 Codex 会话以加载 [AGENTS.md](../../AGENTS.md)。其他客户端按实际规则加载方式提供入口和必要片段。只有对话能力时，按可用资料分析并给出待执行步骤。
- 用户提供真实目标、获准资料和完成条件。工程、验证和上线沿用现有流程，新后台的参考入口见[需求手册](discovery.md#g2-prototype)。
- 从旧版迁移时，由人把原件和人工记录移入 `sources/`。停用旧问答前，AI 将已有结论和依据保存到对应需求、方案或验收记录，将仍存在的实际阻塞及恢复条件写入项目状态或对应任务。保留仍被引用的入口。
