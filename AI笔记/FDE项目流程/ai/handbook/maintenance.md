# 长期迭代与文档维护

> AI维护，按需执行。业务批准、语义复用和 OPEN 状态分别以 [验收](../records/acceptance.md)、[需求](../specs/requirements.md)、[澄清台账](../records/clarifications.md) 为准。

流程版本：FDE1.3。项目采用来源与版本只记 [项目概况](../specs/project.md)，通用流程升级不改变业务 BL、原型版本或确认方式；同步前比较项目差异，保留既有约定和记录。

## 日期与迭代顺序

| 来源 / 用途 | 文件名与顺序 |
| --- | --- |
| 人提供的需求原件、访谈原始记录、录音、业务表格等 | `YYYYMMDD-原名称.ext`；已有日期前缀保留，不重复添加。仅转换/OCR/转写或忠实摘录不改变资料来源归类 |
| AI 整理的任务、访谈纪要、变更、验证记录 | `TASK-001-english-name.md`、`MEET-001-english-name.md`、`CR-001-english-name.md`、`RUN-001-english-name.md`；序号递增、项目内唯一，不因换日期/批次重置 |
| AI 阶段产物、截图或测试报告 | 沿用原型版本、PAGE/TEST/RUN 等可追溯编号作为前缀，正文或所关联记录标明生成日期；不另造日期序号 |
| AI 提炼的需求与验收条件 | 依已有 `REQ-001` / `AC-001-01` 标识关联和排序；现行汇总/模块规格保持稳定路径，不为增加文件名前缀复制一套需求 |

- 人提供资料的前缀优先使用可核实的形成/访谈日期；未知则用收到日期，并在来源记录中注明日期含义。两者均未知时保留原名标待补，不用文件系统时间或本轮整理日冒充。记录原名、形成日、收到日、来源及版本；正文不改。人提供原始访谈与 AI 整理的 MEET 纪要分别保存并互链。
- 两类记录都区分创建、最近更新、事件/沟通、确认及生效日期，新增日期用 `YYYYMMDD`；需要时记实际时间和时区。AI 文件按序号排序，不加日期前缀；人用资料的前缀不随后续整理更新。历史 `YYYY-MM-DD` 格式和执行事实保留。
- 每个需求/沟通条目保留提出或首次登记日期；实质变化追加“日期＋编号/版本＋差异＋来源/决定依据”，关联前序记录。不能把创建、答复、批准、实现、验证混为一次事件；同日依编号/版本/前序表达顺序，不编造精确时间。
- `README`、`AGENTS`、人用入口、现行规格与运行代码保持稳定路径，通过正文的日期/版本/变化记录迭代；同文件内 RUN/OPEN/UAT 各自带日期。模板保留 `TEMPLATE.md` 和日期占位，框架已有代码/迁移命名规范优先沿用。
- 日期不代表批准或优先级，序号不代替有效 BL。已固定批准包不重命名；其他文件改名时保留编号、锚点、原名映射并修正链接，不改写历史确认或命令。

## 1. 何时检查，谁执行

本轮 AI 在下列时机检查，你核对业务与证据结论；整理纳入收尾，不建定时任务或人工编号计数器。

| 触发 | 动作 |
| --- | --- |
| 新资料/需求 | 检索现行与归档索引，复用同义 REQ/AC，追加来源；改变有效规则走 CR |
| 候选包批准 | 按验收记录核对完整组合、起点、批准映射与冲突；切换前重读当前 BL |
| 第二个独立业务模块 | 按下节拆规格，保留全局索引、共享规则、编号与链接 |
| TASK 或独立功能收尾 | 回写结果和遗留项，更新项目状态及最新检查点，已完成事项退出当前工作；按第 3 节核对本轮可归档项。没有 TASK 就更新已有入口 |
| 交付范围结束 | 集中核对该范围剩余历史；无符合项时在收尾注明“无需归档” |
| 拆分/归档/重开 OPEN | 按第 4 节核对链接、锚点、唯一当前字段，保留未决与有效依据 |

收尾由 AI 回写事实，更新项目状态，并以最新检查点替换 TASK 中的旧检查点。只刷新可从现行记录重建的导航与议程，保留人指定的议程、已填写的答复和未吸收的新输入。本轮符合第 3 节的条目列为归档候选，附编号和目标位置。执行迁移时按第 4 节核对旧入口与唯一证据；无候选时无需新增记录。结构检查沿用 `check_context.py`，业务合并、批准和验收仍按各自证据判定。

## 2. 按职责拆分现行规格

首次出现第二个可独立维护的业务模块时拆分；同一链路的几个页面不算多个模块，不按行数或迭代切割，已有模块沿用原落点。

- `ai/specs/requirements.md` 保留全局索引、术语、共享规则；模块唯一详情放 `ai/specs/requirements/<module>.md`，共享内容只引用。
- `ai/specs/solution.md` 保留工程、公共架构、命令与模块索引；独立方案放 `ai/specs/solutions/<module>.md`。
- 原型保留实际入口，不每期复制整套资料；候选/已批准版本由固定提交或评审包区分。

仅实际拆分时建目录。不改编号或业务含义；原入口显式保留被引用的锚点（含旧标题自动锚点）及转向，导航标题不以真实编号开头，编号定义只留目标。发现业务差异单独处理，不当排版调整带过。

## 3. 哪些历史可以移走

任务收尾只核对本轮涉及的记录。MEET/TASK/CR/RUN/UAT/FB 在结束后，如无待查看、待答复、待复验或其他后续动作，且已退出当前依据，可归档。旧阶段和移交正文在交付收尾核对。归档放入 `ai/archive/<scope>/`，按类型/编号命名，如 `RUN-001.md`、`stages-and-handoff.md`；重名加版本，不覆盖。

已关闭并回写的 OPEN 历史可归档；同一 OPEN 后续已结束轮次加日期/版本，不另编号。重开后的未决轮次留现行。现行入口必须保留：

- 当前有效 REQ/AC、当前 BL 及其继承/新增批准入口、当前 AC 状态与最新适用 RUN/UAT。
- 原编号、已被引用的标题/锚点、历史转向；旧阶段的范围、版本、结论索引。
- OPEN 全部索引行、固定锚点、当前结论/适用范围、历史链接；状态/答复人/动作/期限只存索引。
- 未决问题、待复验、未关闭缺陷、未完成轮次。

历史摘要或索引开始妨碍定位当前事项时，按范围合并历史入口，现行页只保留必要索引字段和原锚点短跳转。全量历史按编号或范围检索；已确认与取消的需求沿用原编号，保留决定依据。移除重复正文前先核对唯一记录及链接，原始材料、原获批包和批准证据原样保存。

## 4. 每次迁移按此顺序完成

1. 列出“原文件/编号/锚点→目标”，划出当前有效和未决内容，不随历史移走。
2. 写目标并按新父目录修正正文相对链接，包括目标未移动但相对关系变化的报告。
3. 原位置显式保留旧锚点及转向，旧标题自动锚点也须保留；导航标题可写“已迁移：REQ-001”，不再以编号开头。跨阶段复用 BL 时链接原登记，不重复定义；不能用文件级跳转替代已引用片段。
4. 先日常检查，再用 `--check-file` 逐个指定迁移目标；多目标重复传参，均相对项目根，不通读旁边历史。

```sh
python3 ai/scripts/check_context.py
python3 ai/scripts/check_context.py --check-file 'ai/archive/purchasing-phase-1/RUN-001.md' --check-file 'ai/archive/purchasing-phase-1/OPEN-001.md'
```

示例路径须换成真实目标。缺失、非 Markdown、项目外路径或符号链接会失败，不能省掉失败文件后宣称通过。

5. 脚本检查本地目标、已读 Markdown 的 ATX 标题/显式锚点、现行编号标题、需求 AC 表及阶段 BL/FB/BUG 表首列和 UAT 条目的定义唯一性、追踪表“已验证”行的实现信息，以及落到本次已读 Markdown 的 BL/RUN 锚点、原型 HTML 登记及设计 token/版本。占位路径和非 Markdown 片段不算已核对；未读 Markdown 需 `--check-file`，且不因此读取其他历史。实现列按整格匹配缺失值，整格“未实现/未开始/未验证”不能标已验证；版本说明内的这些文字不拦截。代码示例、普通引用和指定历史不算现行定义；未指定的归档/原件正文不读取，其片段须迁移时显式指定。HTML 动态路由、其他 Markdown 语法/渲染器、业务结论、实现版本正确性与批准真实性仍需核对。
6. 归属/链接不明就保留原文或恢复，不删唯一依据。将映射、检查与剩余项记本轮 TASK/收尾，已有 RUN 只链接；更新项目状态，维护记录不算业务批准。

## 5. 用这些场景验收维护结果

工具回归运行 `python3 -m unittest discover -s ai/scripts -p 'test_*.py'`：应发现断链/失效锚点、重复定义、已验证行缺引用、遗漏登记页面；指定一个历史不读其他历史，多目标逐个检查，项目外/符号链接拒绝。为 REQ/OPEN/TASK/CR/BL/RUN 等真实记录保留稳定显式锚点，改名仍保留；AC 可链接所属 REQ 的固定锚点。

另沿链接复核：晚到批准不能覆盖当前组合、冲突先补确认；同义需求复用编号；重开 OPEN 保留旧结论的适用版本和新轮次；模块拆分后原入口仍可定位。脚本不证明这些业务判断，AI 须展示依据。

### 流程变更的固定演练

修改规则后，仅重演受影响场景；复用同一输入，记录工具/模型及流程版本、输入入口、实际产出、遗漏与耗时到本轮 TASK/RUN。先验证问题，再增加规则；未执行的语义演练保持未验证，工具单测不代替演练。不另建演练台账。

| 起点与新输入 | 应观察到的结果 |
| --- | --- |
| 当前BL已前进，收到旧起点候选包批准 | 保留当前组合，核对差异/冲突与批准映射；冲突未补确认不切换 |
| 已关闭OPEN收到新范围的矛盾答复 | 原编号重开，旧结论保留适用版本，当前轮次待澄清 |
| 答复已保存、回写未完成时中断再继续 | 找到原答复并补回写；不覆盖答复或提前移除人用问题 |
| 两个模块同改一个AC，或规格拆分后继续开发 | 现行定义唯一，原锚点可定位；冲突显式处理，受影响AC待复验 |
| 一个功能已收尾，新会话只收到“继续” | 从项目状态和当前 TASK 找到有效版本及下一项已授权工作；已完成项退出当前工作，必要的旧证据仍可按原编号定位 |
| 评审前原型小改；另测带新答复或共享依赖的变更 | 小改按原型入口接续；有新答复或共享影响时定点展开原话、规则与回归。用相同任务比较首次编辑前的读取量，核对版本、授权、验证和结果 |

## 并行与带问题推进

不增加阶段或降低门槛：

1. **定位影响**：OPEN 写阻塞 REQ/AC、阶段、恢复条件。查接口、数据、权限、状态、字典、配置、外部依赖；不同菜单/文件不足以证明独立，无法排除的联动保持阻塞，答复人/期限只存 OPEN 索引。
2. **选可做工作**：未知规则只可整理资料、画待验证草图或做已授权探索；正式开发须自身 G1/G2/G3 及全部依赖满足。阻塞只挂起相关部分，可做下一项独立已授权工作，原问题/任务保留。
3. **保持承诺边界**：项目状态逐行指向各范围/阶段/AC，验收记录存正式结论。拆分、排除、延期原承诺须明确确认，改变已批准范围走 CR；不能自行圈“已确认子集”过关，G4/G5 仍覆盖被验范围全部有效 AC。未来问题不自动阻塞本期，但无影响须有依据。
4. **隔离写入、串行整合**：一个项目一个完整有效 BL。整合 AI 串行登记 REQ/AC/OPEN/TASK/CR/BL/RUN 并回传编号；其他任务用临时号，不抢共享编号。分配独立路径/工作区；共享规格、项目状态、追踪/验收、接口由整合者重读再合并，保留其他行，不用旧快照覆盖。交接读文件/检查点，不靠聊天恢复，人的确认权不变。
5. **核对后生效**：重读当前 BL、共享文件、任务起点；旧起点合入期间已生效内容，冲突仅停依赖部分，批准按验收规则。记录合入代码版本，核对共享契约并做集成回归；旧 RUN/UAT 不自动代表新组合通过。失败保留现场，从最后已核实检查点恢复。

这些规则不提供锁或事务。无法保证写入归属、隔离和串行整合时改顺序执行，不要求人维护额外排程或锁台账。
