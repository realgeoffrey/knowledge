# 单元测试与测试规范要点

---

## 关键词解释

### 原则与缩写

| 关键词 | 解释 |
|---|---|
| **Unit Test（单元测试）** | 在隔离条件下验证一小段逻辑（通常方法/类）的自动化测试。不碰真实 DB、网络、文件系统等（见 Feathers 规则）。 |
| **FIRST** | 好单测五特征：**F**ast 够快才愿常跑；**I**solated 用例互不依赖；**R**epeatable 任意环境结果一致；**S**elf-validating 用断言自动判对错；**T**imely 及时编写（贴近实现/TDD）。 |
| **AIR** | 阿里 P3C 提法：**A**utomatic 全自动（禁人肉看日志）；**I**ndependent 独立；**R**epeatable 可重复。与 FIRST 高度重叠。 |
| **四支柱**（Khorikov） | 衡量测试价值：①**防回归**（能抓缺陷）②**抗重构**（改实现不误红）③**反馈快**④**可维护**。①②最重要；绑死实现细节会牺牲②。 |
| **测行为不测实现** | 断言对外可观察结果（返回值/状态/异常/副作用），不断言私有步骤、内部调用顺序。实现变、行为不变 → 测试应仍绿。 |
| **Clear / Complete / Concise / Resilient** | Google TotT：清晰可读、信息自洽完整、无噪音、行为不变则测试不必改（韧性）。 |

### 策略与形态

| 关键词 | 解释 |
|---|---|
| **测试金字塔** | Mike Cohn / Fowler：底层大量快单测 → 中层适量集成 → 顶层极少 E2E。越高越慢越脆，故数量越少。 |
| **冰淇淋甜筒** | 反模式：E2E/UI 过多、单测过少 → 慢、脆、难维护。 |
| **沙漏** | 反模式：两端（单测+E2E）多、中间集成空 → 协作问题漏测。 |
| **Testing Honeycomb** | Spotify 微服务策略：以服务边界 **Integration** 为主；复杂内部逻辑才写 Implementation Detail；跨服务 Integrated/E2E 尽量少。 |
| **Feathers 规则** | 「不算单测」若：访问 DB、走网络、碰文件系统、不能与其他单测并行、要改环境配置才能跑。这类测试有价值，但须与真单测**分套件**，保证单测始终快。 |
| **E2E** | End-to-End，端到端：模拟真实用户路径，穿过多层系统。贵、慢、易 flaky，只保关键路径。 |
| **集成测试** | 验证多个组件/服务协作或与真实依赖边界的正确性；比单测慢，比 E2E 窄。 |
| **契约测试（Contract）** | 验证接口约定（请求/响应形状、字段语义）是否被双方遵守，常用于服务间。 |

### 写法与结构

| 关键词 | 解释 |
|---|---|
| **SUT** | System Under Test，被测系统/对象。单测里应对 SUT 用**真实实例**，对其依赖用替身。 |
| **AAA** | Arrange–Act–Assert：准备数据与依赖 → **一次**调用 SUT → 断言。又称 Given–When–Then。 |
| **一测一场景** | 一条用例只验证一条业务规则/一个场景；失败时立刻知道坏了什么。 |
| **Happy Path** | 合法输入下的主成功路径；不能只测它，还须边界与错误路径。 |
| **副作用（Side Effect）** | 除返回值外的可观察影响：写库、发消息、改状态、调外部 API 等。 |
| **魔法值** | 测试里无语义的字面量（如 `"abc"`、`123`）；应提成有含义的常量/变量。 |
| **Fixture / Builder / Mother Object** | 测试数据构造手段：固定夹具、建造者、专门生产测试对象的工厂，减少重复与噪音。 |
| **beforeEach / beforeAll** | 每条用例前 / 整套一次前的初始化。共享可变状态时 `beforeAll` 易导致顺序依赖，单测更常用 `beforeEach`。 |

### 测试替身（Test Double）

| 关键词 | 解释 |
|---|---|
| **Test Double** | 测试中替代真实依赖的统称（xUnit Patterns）。 |
| **Stub** | 按预设返回值/抛错，**提供间接输入**；一般不关心是否被调用。 |
| **Mock** | 既可预设行为，又用于**验证交互**（是否调用、参数、次数）；过度 verify 易绑实现。 |
| **Fake** | 可用的简化实现（如内存 Repository），行为接近真实但无外部 IO。常比一堆 Mock 更稳。 |
| **Spy** | 包装真实对象，可记录调用；部分真实、部分可桩。慎用，易模糊边界。 |
| **古典派（Detroit/Classical）** | 隔离的是「测试之间」；单元是**行为**；通常只替**进程外**依赖（DB/网络等），进程内协作尽量真实。 |
| **伦敦派（London/Mockist）** | 隔离到**类**；协作者大量用 Mock；粒度细，但易过度指定实现、测试更脆。 |

### 测点框架

| 关键词 | 解释 |
|---|---|
| **BCDE** | P3C：**B**order 边界；**C**orrect 正确输入；**D**esign 结合设计/契约；**E**rror 错误与异常路径。 |
| **RIGHT-BICEP** | Pragmatic Unit Testing 检查表：结果是否 Right；边界；反向关系；交叉检查；错误条件；性能特征等。 |
| **CORRECT** | 边界条件口诀：Conformance 格式、Ordering 顺序、Range 范围、Reference 引用、Existence 有无、Cardinality 多少、Time 时间。 |

### 质量与流程

| 关键词 | 解释 |
|---|---|
| **覆盖率** | 被测代码被执行到的比例（行/分支/等）。是**结果指标**，不是目标；高覆盖+弱断言仍可能测了个寂寞。 |
| **变异测试（Mutation）** | 故意改生产代码（变异体），看测试是否失败。测不过 → 断言可能没真正抓住缺陷。 |
| **Flaky** | 同一代码反复跑结果时过时不过。多因时间、并发、顺序、外部依赖。会摧毁对 CI 的信任，必须治理。 |
| **TDD** | Test-Driven Development：先写失败测试再写实现。循环 **Red → Green → Refactor**。 |
| **TDD 三定律** | ①无失败测不写生产代码；②测只写到刚好失败；③代码只写到刚好让测通过。 |
| **弱断言** | 几乎不证明行为的断言（仅非 null、仅未抛异常）；对回归保护弱。 |
| **伪单测** | 挂着单测名字，实际依赖容器/真实中间件，慢且不稳。 |
| **抗重构** | 重构（行为不变、结构变）后测试仍通过；若常误红，说明测了实现细节。 |

## 1. 好测试的标准

| 维度 | 要点 |
|---|---|
| FIRST / AIR | 快、独立、可重复、自动判定、及时写 |
| 四支柱 | 防回归 + 抗重构（最关键），兼反馈快、可维护 |
| 可读韧性 | 清晰、完整、简洁、行为不变则测试不改 |
| 价值 | 保护行为、支撑重构、可执行文档；**不为刷覆盖率** |

**一句话：** 快、稳、独立、自动判定；测可观察行为，不绑实现细节。

---

## 2. 测试策略

```text
        E2E / UI     ← 极少
      集成 / 服务     ← 适量
    单元 / 窄范围     ← 大量   （金字塔）
```

- 越高越慢越脆 → 数量越少；忌冰淇淋甜筒、沙漏
- Google 经验约：**80% 窄范围 + 20% 更广范围**
- 微服务可参考 Honeycomb：重服务边界 Integration，少跨服务 E2E
- 触达 DB/网络/文件/需改配置的测试：与真单测**分套件**（Feathers）

## 3. 单元测试怎么写

### 边界

| 做 | 不做 |
|---|---|
| 测局部行为；真实 SUT + 替身依赖 | 当联调；真实 DB/MQ/HTTP/墙钟/随机源 |
| 测试与生产目录分离 | 起重量级容器只验局部 if/else |

### 结构

- **AAA**：准备 → **一次** Act → 断言；一测一场景
- 命名可读：`XxxTest`、`method_should_expected_when_state`；禁 `test1`
- 断言优先级：返回值 → 状态 → 异常 → 对外副作用
- 禁：弱断言、测试里用逻辑**计算**期望值、过宽 `Exception`

### 替身

| 通常替身 | 通常不 Mock |
|---|---|
| Repository、RPC、缓存、MQ、Clock、IO | DTO、枚举、值对象、纯函数、SUT 自身 |

能 Fake 优于堆 Mock；`verify` 仅当交互本身是契约；倾向古典派「测结果」，避免伦敦派过度 Mock。

### 测点顺序

主路径 → 边界 → 非法/异常 → 依赖失败 → 副作用（BCDE / RIGHT-BICEP / CORRECT 任选作检查表）。

### 数据

最小化；禁魔法值；复用 Builder/Fixture；慎全局 Setup；难测先改设计再堆 Mock。

## 4. 覆盖率、Flaky、流程

| 主题 | 共识 |
|---|---|
| 覆盖率 | 结果非目标；语句常参考 ~70%，行 ~80%；核心看分支 |
| 变异测试 | 检验断言是否真能抓缺陷 |
| Flaky | 必须治理，否则 CI 失信 |
| TDD | Red → Green → Refactor（可选但经典） |
| 补测步骤 | 契约 → 测点 → AAA → 自检隔离与可读 |

---

## 5. 红旗（危险信号）

单测碰真实外部世界；容器测局部逻辑；一测多场景；测私有/过度 verify；测试含业务逻辑；弱断言刷覆盖；E2E 过多；重构就大面积红。

---

## 6. 速记

> **FIRST + 测行为不测实现；金字塔底部要厚；一测一规则用 AAA；隔离外部世界；覆盖率服务于质量，不为数字而测。**
